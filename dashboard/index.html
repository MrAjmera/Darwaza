Razorpay AI Buildathon · Track 01

An authorization gate for AI buying agents — watched live.

Darwaza decides, in code, whether an AI agent is allowed to spend a merchant's money — before Razorpay ever sees the request. This console is a read/demo layer sitting outside that decision path: everything below either displays what the gate already recorded, or triggers the exact same scenarios the CLI's simulate command runs.

Darwaza /dər-vaː-zaː/ — Hindi for door. Three outcomes only: ALLOW, DENY, NEEDS_HUMAN. Zero LLM calls anywhere in that decision.

High-level design

The trust boundary the rest of the system hangs off: everything on the agent's side is untrusted input, including the agent itself. Nothing crosses it as "trusted" until it passes a named check.

Scaling — three stages, one built

"How do you get to 10,000 requests" answered honestly: this system fails at 2 concurrent requests before it becomes slow — see Limitations for the defects that proved it, and how they were fixed.

Stage 1 — built, today

One process. SQLite in WAL mode, per-thread connections. Audit log behind an OS-level lock. Proven correct at 50 concurrent threads × 15 runs against one single-use mandate: exactly one ALLOW, every time.

Stage 2 — designed, not built

Stateless API replicas behind a load balancer. Postgres ON CONFLICT ... RETURNING replaces SQLite's PRIMARY-KEY trick — same idea, multi-instance-safe. Per-merchant audit chains; a shared Redis rate-limit counter.

Stage 3 — named, not built

Redis as a hot cache in front of the durable nonce store; async Razorpay execution off a queue, reusing the idempotency-by-receipt guarantee already built for retries.

policy_engine.evaluate() takes every piece of state as an explicit argument and holds none of its own — swapping the nonce claimer's backing store (SQLite → Postgres) needs zero changes to policy_engine.py itself. That's the payoff of a Stage-1 decision, not a Stage-2 achievement.

Attacks blocked, and the honest limitations

Volunteering weaknesses first, not a formality before Q&A. Six real defects, found by adversarial and concurrency testing, fixed, and now permanent regression tests.

IDWhat brokeFix
D1Replay was check-then-add — 2 concurrent requests on one mandate could both read "unspent"Single atomic INSERT, PRIMARY KEY enforces it
D2Audit log read-tip-then-write raced — concurrent writers forked the chain with no tampering at allOS-level lock around the whole read-then-write
D3Shared SQLite connection across threads — real OperationalErrors, once a raw SystemErrorPer-thread connection + WAL + busy_timeout
D4NEEDS_HUMAN never reserved its nonce — one mandate resubmitted 3× produced 3 approvable ordersevaluate() claims the nonce the moment it reaches NEEDS_HUMAN
D5No lower bound on amount — 0, negative, and NaN all returned ALLOWSchema + runtime both check isfinite(amount) and amount > 0
D6"approved" was committed before the Razorpay call ran — a crash in between looked identical to successNew non-terminal approved_pending_execution state

Adversarial coverage

prompt-injected buyer agent replayed mandate expired mandate cross-merchant token reuse cap-exceeding request poisoned catalog listing forged / tampered signature

42 scored cases in evals/, distinct from the pytest suite — 33% deliberately legitimate traffic, because a corpus that's all attacks can't measure false positives. Both suites run on every push via CI.

Named, not hidden

  • Key rotation and issuance are out of scope — three hardcoded demo principals.
  • Multi-instance coordination beyond Stage 1 is not built.
  • The 50% human-review threshold is a defensible round number, not tuned against real fraud data.
  • decide_with_llm()'s live prompt-injection path needs a real API key and isn't exercised by CI.
  • Razorpay integration stops at order creation — a full payment round-trip needs a checkout frontend.
